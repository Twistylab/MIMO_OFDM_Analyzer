# MIMO-OFDM BER Analysis

Проект моделирует цифровую систему связи **MIMO-OFDM + QAM** и сравнивает качество приёма по метрике **BER** для разных алгоритмов детектирования и эквализации в канале с **AWGN** и опциональным **рэлеевским многолучевым замиранием**.

Основная цель проекта — исследовать, как меняется BER при разных значениях SNR, типах приёмника и режимах декодирования.

## Возможности

- QAM-модуляция и демодуляция через `CommPy`
- OFDM-передача с IFFT/FFT, пилотами и циклическим префиксом
- модель MIMO-канала
- канал с AWGN
- канал с рэлеевским замиранием и многолучевым распространением
- сравнение методов **ML**, **ZF**, **MMSE**
- режимы:
  - без FEC
  - FEC + hard decision
  - FEC + soft decision
- расчёт **BER**
- расчёт **EVM** для ZF/MMSE-сценариев
- параллельный запуск независимых расчётов через `ProcessPoolExecutor`

## Для чего этот проект

Проект подходит как:

- учебный симулятор по цифровой связи;
- база для курсовой/дипломной работы;
- исследовательский стенд для сравнения алгоритмов приёма;
- заготовка для дальнейшего вынесения логики в библиотеку.

## Назначение файлов

### `optimal_decision_ber_analysis_parallel.py`
Главный модуль проекта. Содержит:

- адаптер для QAM-модема;
- MIMO-OFDM тракт передачи и приёма;
- вставку пилотов;
- прохождение сигнала через канал;
- ML-детекцию;
- ZF/MMSE-эквализацию;
- помехоустойчивое кодирование и декодирование Витерби;
- расчёт BER и EVM.

Ключевые классы:

- `QAMModemAdapter`
- `OFDMMIMOTransceiver`
- `DataProcessing`
- `DecisionMethodAnalyzer`

### `ber_multithreaded_computing.py`
Оркестратор параллельных запусков. Запускает BER-анализ для выбранных методов в отдельных процессах и возвращает результаты в виде словаря.

### `main.py`
Основной сценарий эксперимента. По умолчанию запускает расчёты для:

- `M = 16`
- `Nt = 2`
- `Nr = 2`
- `SNR = 0..28 dB` с шагом `2`
- всех методов ML / ZF / MMSE
- канала с AWGN и рэлеевским многолучевым распространением

Скрипт усредняет результаты и сохраняет итоговый график BER.

### `verif.py`
Скрипт верификации. Сравнивает BER, полученный в программе, с эталонными кривыми из папки `ber my vs bertool/bertool/`.

По умолчанию использует:

- `M = 4`
- `Nt = 1`
- `Nr = 1`
- `SNR = -10..6 dB`
- AWGN без многолучевого канала

### `static_method.py`
Вспомогательный модуль.

Содержит:

- генерацию импульсной характеристики рэлеевского канала;
- учебные реализации `dft`, `idft`, `fft`, `ifft`.

> В основной OFDM-цепочке используется `numpy.fft`, а ручные реализации из `static_method.py` полезны скорее как учебные/вспомогательные функции.

## Фиксированные параметры модели

В текущей реализации часть параметров зашита прямо в код:

- число кадров: `10`
- полоса: `240e3`
- шаг поднесущих: `15e3`
- число поднесущих: `240e3 / 15e3 = 16`
- свёрточный код: `Trellis(np.array([7]), np.array([[0o133, 0o171]]))`

Это важно учитывать при интерпретации результатов и сравнении с внешними источниками.

## Запуск

### Основной эксперимент

```bash
python main.py
```

Что делает скрипт:

- запускает серию вычислений BER для выбранных методов;
- усредняет результаты по числу итераций;
- строит итоговые BER-кривые;
- сохраняет рисунок в папку `ber & evm/`.

### Верификация относительно reference-кривых

```bash
python verif.py
```

Что делает скрипт:

- считает BER для SISO-сценария;
- загружает эталонные `.npy` данные;
- строит сравнение с reference-кривыми;
- сохраняет результат в `ber my vs bertool/`.

## Выходные артефакты

Проект сохраняет графики в файловую систему, а не показывает их только интерактивно. Основные выходы:

- `ber & evm/BER vs SNR All methods.png`
- `ber & evm/BER vs SNR All methods (AWGN).png`
- `ber my vs bertool/my program vs bertool.png`

## Интерпретация результатов

- **BER ниже — лучше**.
- Сравнение по SNR показывает устойчивость метода к шуму.
- Сравнение режимов `without fec`, `with fec hard`, `with fec soft` показывает выигрыш от кодирования и мягких решений.
- ML обычно даёт лучшее качество, но требует больше вычислений.
- ZF и MMSE дешевле вычислительно, но чувствительны к условиям канала и размерности системы.

## Ограничения текущей реализации

1. Параметры эксперимента жёстко зашиты в скриптах.
2. Нет единого `requirements.txt` или `pyproject.toml`.
3. Нет тестов.
4. Нет CLI-интерфейса.
5. Нет фиксации `random seed`, поэтому результаты между прогонами могут слегка отличаться.
6. ML-детекция быстро дорожает при росте `M` и `Nt`.
7. Выходные пути и reference-данные заданы строковыми литералами.
8. Репозиторий содержит служебные файлы macOS.

## Рекомендации по развитию проекта

### 1. Вынести конфигурацию экспериментов из кода
Лучше хранить параметры в `yaml/json` или передавать через `argparse`.

### 2. Добавить воспроизводимость
Рекомендуется фиксировать seed, например:

```python

```

### 3. Добавить `requirements.txt` или `pyproject.toml`
Это упростит запуск проекта на новой машине.

Вместо строковых путей лучше использовать `Path` и автоматически создавать каталоги через `mkdir(parents=True, exist_ok=True)`.

Минимально полезны тесты на:

- размеры массивов;
- корректность форм матриц;
- поведение multiprocessing-обёртки;
- свойства `fft/ifft` и `dft/idft`.

Стоит добавить `.gitignore` и удалить:

- `__MACOSX/`
- `.DS_Store`
- временные картинки, если они не нужны как эталонные артефакты

### 7. Разделить код на библиотечную и сценарную части
Рекомендуемая будущая структура:

## Best practices для использования этого проекта

- запускайте эксперименты в отдельном виртуальном окружении;
- сохраняйте параметры прогона рядом с графиками;
- не сравнивайте кривые, если изменили модель канала, но не зафиксировали это явно;
- для сравнений между версиями фиксируйте seed и набор SNR;
- не включайте все методы сразу для очень больших `M` и `Nt`, если важна скорость;
- держите reference-данные отдельно от исходников;
- не смешивайте исследовательские скрипты и библиотечный код в одном модуле.
